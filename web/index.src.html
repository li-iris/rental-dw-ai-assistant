系统是怎么理解的

问题先被解析成一个受约束的「查询意图」，再由模板生成 SQL。语言理解不直接写 SQL，所以不会查不存在的字段，也不会被诱导去改数据。

数据质量：测试只负责发现，怎么处理是判断

数仓分层：原始层 → 清洗层 → 模型层

仿 dbt 的写法：每个模型是一个 SQL 文件，用 {{ ref('…') }} 引用上游，运行器按依赖排序后建表并生成血缘。问题行只打标、不删除，事实表行数和原始表完全对得上，任何一个数字都能追到来源文件和行号。

指标口径

  • 新签租约：每条押金登记 = 一份新签租约。数据里没有续租，所以反映的是「新上市房源的成交租金」，不是所有在租房屋的平均租金。
  • 可分析的行：房型为公寓 / 独立屋 / 联排（排除车位、房间等 Other 和 Unknown），周租金 80–5000 澳元，邮编能匹配到区域。
  • 租金：默认用中位数，不受极端值影响；均值和 25 / 75 分位也可以问。
  • 地区：郊区按邮编近似（一个邮编可能包含几个郊区）；同名时默认取郊区，说「市 / council」才取地方政府区（LGA）。
  • 时间：郊区 / 邮编默认看最近 3 个月（样本更稳），大地区默认看最近 1 个月；排名只比较样本 ≥ 30 份的分组。

评测：标准答案是手写 SQL

每道题都手写一条标准 SQL，在 SQLite 上执行；系统生成的 SQL 也在 SQLite 上执行，结果一致才算对。另外核对浏览器里算出的数字和 SQLite 是否一致。三套题分开报：开发集调规则用；留出集写完规则才写；第二留出集是看过留出集的错误、改完规则以后才写的新题，不再据此调规则。

留出集暴露的问题（已修，改完又写了第二留出集）

  • 年份被当成邮编：「September 2026」里的 2026 恰好是 Bondi 的邮编。改为年份紧挨月份词时不当邮编。
  • 「Greater Sydney」被识别成悉尼市区：Sydney 既是 CBD 郊区，也是大悉尼。问排名或说 Greater Sydney 时取大悉尼。
  • 没收录的地名被截短：「Springfield Heights」被当成 Springfield。后面还跟着大写单词时改为反问，不猜。

数据

  • NSW Fair Trading「Rental bond lodgement data」，2025 年 10 月 – 2026 年 10 月，13 个月度文件，共 338,947 行（nsw.gov.au 公开数据）。由 GitHub Actions 定时下载进仓库。
  • 邮编 → 区域参考表：australianpostcodes（公开数据集），取 NSW 部分。

大模型放在哪里

  • 规则解析覆盖大部分常见问法，零成本、可解释、可评测。
  • 规则答不了或理解错时，可以点「请大模型重新理解」。大模型只能返回同一个 JSON 意图结构，返回后照样过校验（指标、地区、月份都必须是数据里有的值）、照样由模板生成 SQL。大模型不碰数据，也不写 SQL。
  • 大模型功能需要在 claude.ai 登录后使用；未登录时只用规则。

局限

  • 只有新签租约，没有续租和空置率，不能代表全部租客的负担。
  • 没有房屋面积、新旧、是否带家具等信息，同样「两房」差别可能很大。
  • 规则解析对没见过的说法会理解错（见评测页仍答错的题），这也是保留大模型兜底的原因。
