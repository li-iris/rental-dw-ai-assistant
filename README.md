# rental-dw-ai-assistant：租赁数仓 AI 助手

个人项目。数据是 NSW Fair Trading 公开的真实租房押金登记数据：2025 年 10 月到 2026 年 10 月，共 13 个月、338,947 份新签租约。

> **一句话**：把政府每月发布的 Excel 搭成分层数仓（原始 → 清洗 → 模型），配 15 条数据质量测试，再在上面做一个能用中文 / 英文问数的助手。助手先把问题解析成受约束的查询意图，再由模板生成 SQL，所以不会编造字段。评测用手写 SQL 作为标准答案，留出集答对率 75%。

## 解决什么问题

业务方想知道「Randwick 两房公寓现在多少钱」「悉尼哪个区一房最贵」，通常要等数据团队写 SQL。这个项目做两件事：

1. **数据可信**：先把数据管好，包括分层建模、口径统一、问题行打标、每个数字都能追溯到来源文件和行号；
2. **问数自助**：在可信的数据上，让业务方用自然语言提问，同时把系统的理解（意图 + SQL）摊开给人看，方便核对。

## 数仓

| 层 | 模型 | 说明 |
|---|---|---|
| 原始 raw | `raw_bond_lodgements`、`raw_postcodes` | 原样装载，带来源文件、行号、装载时间 |
| 清洗 staging | `stg_bond_lodgements`、`stg_postcodes` | 类型转换、编码解码；只转换不删行 |
| 模型 marts | `dim_postcode`、`fct_lodgement`、`mart_rent_monthly` | 一个邮编一行的维度表；每份租约一行的事实表，带「可分析」标记；月度指标表 |

`dw/run.py` 是一个极简的 dbt 式运行器：模型就是 SQL 文件，用 `{{ ref('x') }}` 引用上游；运行器按依赖关系拓扑排序后建表，并输出血缘 `results/lineage.json`。用 SQLite 是为了零依赖、可复现，SQL 用的是标准写法（CTE + 窗口函数），可以直接迁到 PostgreSQL / dbt。

数据由 GitHub Actions（`.github/workflows/fetch.yml`）从 nsw.gov.au 下载进仓库。

## 数据质量：测试发现了什么，怎么处理

15 条测试，分 error / warn / info 三级，每条都写了「处理决定」。真实踩到的三个坑：

- **9 月的文件只读到 4 行**：2026 年 9 月的 Excel 打开后默认显示「字段说明」sheet。按默认 sheet 读，整月 2.6 万行会悄悄丢失。改为按表头找数据 sheet，并加「每个文件行数 > 1000」的测试兜底。
- **参考表有一整列是错的**：公开邮编表的 `SA4_NAME_2021` 列，NSW 全部写成「Sydney - Sutherland」，Randwick、纽卡斯尔也不例外。改用 `sa4name`，并保留测试防止回退。
- **完全相同的行有 3.2 万组**：数据没有租约编号，同一栋楼同一天按同价出租多套是正常的，无法判定为重复登记，所以不去重，只记录在案。

其他：房型编码异常 31 行（疑似和卧室数串列，打标为 Invalid）；租金在 80–5000 澳元之外的 432 行（车位 / 储藏间 / 多打一个 0）隔离、不进指标。最终 92.4% 的行可进入指标，事实表行数与原始表完全一致。

## 问数助手

```
问题 ──规则解析──▶ 查询意图(JSON) ──校验──▶ 模板生成 SQL ──▶ 执行 ──▶ 回答 + 意图 + SQL
            └─(规则理解错时)大模型只返回同样的 JSON ─┘
```

- **意图而不是 SQL**：指标（中位数 / 均值 / 数量 / 分位数）、地区（郊区 / 邮编 / LGA / 大区 / 大悉尼 / 全州）、房型、卧室数、月份、分组、同比环比，都只能取语义层里定义好的值。
- **拒答与反问**：房价、预测、其他州、个人信息直接拒答；地名对不上就反问，不猜。
- **小样本保护**：排名只比较样本 ≥ 30 的分组；单点结果样本少会提示。
- **大模型兜底**：页面上「请大模型重新理解」把问题交给大模型，但它只能返回同一个 JSON 结构，返回后照样过校验、照样用模板生成 SQL。
- **同一套引擎跑两处**：`assistant/engine.js` 在浏览器里直接用 31 万行数据（压成 2.2 MB 二进制），评测时在 Node 里跑，生成的 SQL 再交给 SQLite 执行核对。

## 评测

每道题都有手写的标准 SQL；系统生成的 SQL 和标准 SQL 都在 SQLite 上执行，结果一致才算对。

| 题集 | 题数 | 答对率 | 说明 |
|---|---|---|---|
| 开发集 | 25 | 100% | 调规则用 |
| 留出集（第一次跑） | 16 | 69% | 规则写完后才写的题 |
| 留出集（修复后） | 16 | 94% | 已被调过，仅供参考 |
| **第二留出集** | 12 | **75%** | 修完之后新写、不再据此调规则，代表真实水平 |

所有题上，浏览器里算出的数字和 SQLite 执行同一条 SQL 的结果完全一致。

留出集暴露并修复的问题：「September 2026」里的 2026 被当成 Bondi 的邮编；「Greater Sydney」被识别成 CBD；没收录的「Springfield Heights」被截成 Springfield。第二留出集仍答错的题：「最高的 3 个区」没识别成排名问法；「一房和两房」只取了一个卧室数；「买一套」是问房价却没拒答。这些都是规则覆盖不到的说法，也是保留大模型兜底的原因。

## 运行

```bash
pip install openpyxl
python -m dw.ingest        # xlsx → raw 表
python -m dw.run           # 建模（staging → marts）+ 血缘
python -m dw.dq            # 数据质量测试 → results/dq.json
python -m dw.export        # 导出浏览器数据
python -m assistant.run_eval   # 评测（需要 Node）
python -m unittest discover -s tests -t .
node assistant/cli.js "Randwick 两房公寓现在租金多少"
```

## 局限

- 只有新签租约，没有续租和空置率；没有面积、房龄、是否带家具，同样「两房」差别可能很大。
- 郊区按邮编近似，一个邮编可能包含几个郊区。
- 规则解析对没见过的说法会理解错（见评测），大模型兜底需要登录 claude.ai。

**技术栈**：Python · SQL（SQLite，CTE / 窗口函数 / 分位数）· dbt 式分层建模与血缘 · 数据质量测试 · GitHub Actions · 原生 JS（意图解析 + 列式执行）· 大模型结构化输出 · unittest
